### 1b. Charter law #1 — the core is `no_std` + `alloc`, `std` is opt-in


With no feature the crate compiles as a `no_std` + `alloc` library: the frame
codec, the JSON emitters, the selector and the watch accounting (bounded

## 9. Honest limits the founder should rule on for Wave 4's gate

These are named, not hidden (honesty law):

1. **`net connections` / `net ports` / `watch connections`.** Doc 04 §4 and doc
   06 route these to the socket family, and `socket.capnp` declares no
   all-sockets enumeration (the socket batch's gap). The CLI answers exit 3
   (`notSupported`, `serviceUnavailable`) naming the owning batch and the
   per-socket read that does exist (`socket info <id>`), instead of inventing a
   route. **Wave 4 ruling: either add `listSockets` to `socket.capnp` (the
   additive-ordinal path, like the 7 network gap methods) or keep the scope-out
   with this reason published.**
2. **Subscription drop reporting.** The wire's triplets are proven
   (`subscribe`→first event→`pull`→`cancel`) and the drop counter is
   mathematically complete and unit-tested (`watch::account_gap`), but the
   network event structs carry no per-event `sequence` (cli.capnp's job events
   do; the network family's do not), so `watch` reports delivered + idle and
   computes drops only when a family supplies a sequence. **Wave 4 ruling:
   add a `sequence` field to the network subscription event structs, or accept
   delivered+idle as the honest contract for network.**
3. **`net profile` / `export` / `import` / `history` / `ui`.** CLI-local
   workflows (doc 04 §5): profile files are a hand-written TOML subset (the
   crate's only dependency is the contract), export writes stdout (the CLI
   never writes a file — law #8), import and `profile apply` issue real
   contract calls per step and stop at the first failure naming it. True
   transactional networking is not a contract guarantee and help says so.
4. **`wifi connect` credential.** `wifiConnect` takes a `T.SecretKeyId`; the
   passphrase is resolved through the secret service before the call (the
   cleartext path is dead by schema). The CLI passes id 0 and `--verbose`
   names the call; the real secret round trip is the secret-service batch's
   seam.
5. **`firewall allow|deny` / `routes add|remove` replace-set merge.** Implemented
   as an honest read→mutate→`setFirewallRules`/`setRoutes` copying every
   readable field, and the JSON shows the set being replaced (doc 06 §5.2).
6. **Cross-platform (L8).** The grammar and output shape are platform-neutral
   and the transport's non-unix path is an honest `unavailable` stub; the build
   box has no macOS/Windows targets installed (`rustup target list --installed`
   shows linux + bare-metal only), so a cross-target BUILD proof is not
   possible here without mutating the toolchain. **Wave 4 ruling: run the
   `--target x86_64-pc-windows-gnu` / `aarch64-apple-darwin` check once the
   targets are installed; the code carries no platform noun in its grammar.**
7. **Scope-out honoured:** `public-ip`/`whois`/`speed` → web batch; `wol` →
   hardware; `hostname` → system; mDNS/SSDP LAN discovery → own batch;
   `firewall on/off` global switch → firewall batch. The CLI does not invent
   routes for them, and doc 06 §2's row for them is the honest gap answer.

## 8b. Completions — generated from the registry, honest by construction (L5)

`src/completions.rs` renders a completer for bash, zsh, fish and elvish from the
ONE registry table (`registry::TASKS`) that `--help` also reads. Nothing is
hand-written per shell, so the two surfaces cannot drift: a task exists in the
table only when its `cmd-*` feature is compiled, so an uncompiled family is
never completed and never advertised.

The honesty law applies to completion exactly as it applies to help:

* a task the service reports unavailable (`listUnavailable @13`) is withheld and
  the human views name the exact hidden path (`wifi scan`), not just the word;
* a shell whose completer shape the registry does not express refuses with
  exit 2 naming the shell and the shells that ARE expressed — never a fake
  completion;
* with no service reachable the completions still work (the local registry is
  the source) and say `availability is UNVERIFIED`;
* the selector flag is offered only when a task in THIS build lists a contract
  type (a dns-only build does not offer `--where`, because there it does
  nothing).

`net install completions [--shell S] [--path P]` writes the generated completer
ONLY where the user points — the CLI never writes a system path silently — and
`--dry-run` prints what it would write and writes nothing.

```
$ net completions bash | head -3
# net — bash completion, generated by `net completions bash`
# The registry data the same `net --help` reads; a command that cannot
# run on this host is not completed.

$ net --json completions | head -c 120
{"completions":[{"task":"status","verbs":[],"flags":["--json","--quiet",...
```

Test totals: 10 completion tests (`tests/completions.rs`): every shell
completes the registry, the refusal, the JSON corpus, the withheld filter,
install-without-path, dry-run-writes-nothing, install-writes-where-pointed,
help/completions agreement, and the no-service UNVERIFIED case.

## 9b. Cross-platform statement (L8) — verified by INSPECTION, not by toolchain change

The build box has no macOS/Windows targets installed, and installing one is a
toolchain mutation the founder reserved (ruling (3)). This section is therefore
an inspection of the CODE, with every claim naming the file and line that backs
it. Nothing below was verified by a cross-compile; it is stated as such.

**What the code says (read, not guessed):**

| Surface | Where | Cross-platform status by inspection |
|---|---|---|
| Unix socket transport | `src/transport.rs:53-57, 185-198` | The `UnixStream` variant and its connect arm are `#[cfg(unix)]`. On a non-unix target the variant is a `PhantomData` stub that `Connection::connect` never constructs (the `#[cfg(not(unix))]` arm returns an error first), so no silent no-op write is reachable. |
| TCP transport | `src/transport.rs:196-204` | `std::net::TcpStream` — portable; no cfg. |
| Default target selection | `src/remote.rs:139` | The default is the unix socket `$SMART_SERVICE_SOCKET` or `/tmp/smart-service.sock` on EVERY platform. macOS has AF_UNIX, so the default works there unmodified; Windows does not, and the default then fails with a reason that names the fix (`--addr host:port` / `@host:port`), exit 3 — not a fabricated success. |
| TTY / colour policy | `src/render.rs:56-60` | `std::io::IsTerminal` (std, portable) + `NO_COLOR`. No platform noun. |
| File writes | `src/completions.rs:282`, `src/cmd/net.rs:1689` | `std::fs::File::create` / `read_to_string` — portable. `net install completions` writes only the path the user names; `net export` writes stdout only. |
| The `no_std` core | `cargo check -j6 --no-default-features` | Compiles with no operating system at all (see §1b), so nothing in the core is platform-bound. |
| Grammar and output shape | `src/cmd/**` | No platform noun enters the grammar or the JSON keys; availability differs in data only (grammar law #10). |

**What a macOS build would additionally require:** nothing by inspection — the
unix transport is `#[cfg(unix)]` and macOS is unix; the `rustup target add
aarch64-apple-darwin` step is the only thing a gate would need to run, and it is
not performed here.

**What a Windows build would additionally require:**
1. `rustup target add x86_64-pc-windows-msvc` (or `-gnu`) — NOT performed.
2. The default transport would be unusable, so a Windows user MUST pass
   `--addr host:port` or `@host:port`; the CLI says exactly that when the
   default is tried (the code path is `#[cfg(not(unix))]` in `transport.rs`).
3. A named-pipe transport (`\\.\pipe\smart-service`) is the platform's
   AF_UNIX equivalent and does not exist in this crate. It is a deliberate
   SCOPE-OUT, not a defect: the contract's transport set is served over TCP on
   Windows, and the honest answer for the default path is the exit-3 reason
   above. Adding it is a future method/transport decision, not a client fix.

**Honest summary:** the CLI's grammar, JSON shape, help, completions and
honesty law are platform-neutral by construction and by inspection. The
platform-specific surface is exactly one cfg-gated transport arm, and both of
its outcomes are honest (works on unix; names the alternative on non-unix). The
untested claim is the BUILD itself on a foreign target, which the founder
reserved.
